# Quy ước Database Migration (Flyway)

Tài liệu này hướng dẫn **thay đổi schema DB** (thêm bảng, thêm cột, thêm giá trị enum...) cho
mọi thành viên. Đọc mục [4. Quy trình](#4-quy-trình-thêm--sửa-bảng) trước khi đụng vào entity
hoặc file migration.

## Tóm tắt 1 phút

| Chủ đề | Quy ước |
|---|---|
| File migration nằm ở đâu | `src/main/resources/db/migration/` |
| Đặt tên | `V<yyyyMMdd_HHmm>__<module>_<mô_tả>.sql` — **2 dấu gạch dưới** sau version |
| Ai tạo bảng | **Chỉ Flyway** (file SQL). Hibernate KHÔNG tạo/sửa bảng, chỉ map entity vào bảng có sẵn |
| Sửa entity (thêm field, đổi kiểu...) | **Bắt buộc** viết migration mới đi kèm, nếu không app không khởi động |
| File đã chạy (đã merge/đã push) | **KHÔNG BAO GIỜ sửa/xoá/đổi tên**. Muốn đổi → viết file mới (`alter table ...`) |
| Không muốn viết SQL tay | `scripts/db/generate-ddl.sh` sinh DDL từ entity (xem [mục 4](#4-quy-trình-thêm--sửa-bảng)) |
| Trước khi mở PR | `scripts/db/verify-migrations.sh` phải ra ✅ |
| Foreign key | Có FK thật ở DB cho mọi quan hệ, **kể cả giữa các module** (entity vẫn dùng `Long xxxId`) |

---

## 1. Flyway chạy thế nào

1. Mỗi lần app khởi động (`./gradlew bootRun`, test, deploy), Flyway quét
   `classpath:db/migration`.
2. Flyway đọc bảng **`flyway_schema_history`** trong DB — bảng này ghi lại từng migration đã
   chạy kèm **checksum** (mã băm nội dung file).
3. File nào chưa có trong bảng đó → chạy **theo thứ tự version tăng dần**, rồi ghi vào bảng.
4. File đã chạy mà **nội dung bị sửa** → checksum lệch → app **không khởi động**.
5. Sau Flyway, Hibernate chạy `validate`: so entity với bảng thật, thiếu bảng/cột hoặc sai kiểu
   → app **không khởi động**.

> So với NestJS/C#: giống TypeORM migration / EF Core Migrations, nhưng file là **SQL thuần**, và
> **không có lệnh tự sinh migration từ diff** như `prisma migrate dev` hay
> `dotnet ef migrations add`. Repo có script hỗ trợ ở mục 4 để bù lại.

## 2. Hiện trạng schema

Toàn bộ schema theo thiết kế DBML đã có migration (38 bảng, 90 foreign key):

| Version | Nội dung |
|---|---|
| `V20260927_1500` | `specialties` (module mẫu `doctor`) |
| `V20261016_1000` … `_1012` | Tạo bảng, **1 file / module**: auth → facility → employee → doctor → patient → schedule → catalog → company → appointment → examination → payment → violation → notification |
| `V20261016_1100` | `created_at default now()` cho mọi bảng |
| `V20261016_1200` … `_1210` | Foreign key theo DBML (kể cả giữa các module) + index cho cột FK hay tra cứu, **1 file / module** |
| `V20261016_1300` | `updated_at default now()` cho mọi bảng |

Bảng thuộc module nào thì xem tên file (`..._<module>_create_<module>_tables.sql`).

## 3. Công cụ

Cả 2 script dùng **Postgres tạm** (container riêng, cổng `55432`, tự xoá khi xong) — **không
đụng DB dev** của `docker compose`. Cần Docker đang chạy. Đổi cổng nếu bị chiếm:
`SCHEMA_DB_PORT=55433 scripts/db/verify-migrations.sh`.

| Script | Làm gì |
|---|---|
| `scripts/db/generate-ddl.sh [file]` | Hibernate sinh `create table`/index/FK từ **entity hiện tại** ra `build/schema/generated-ddl.sql` (mặc định). Chỉ là **bản nháp** để copy |
| `scripts/db/verify-migrations.sh` | Chạy **toàn bộ** migration trên DB trống + Hibernate `validate`. In số migration/bảng/FK. Lỗi → in log và exit 1 |

## 4. Quy trình thêm / sửa bảng

1. **Sửa entity** (thêm class mới, thêm field...) theo quy ước trong README.
2. **Sinh DDL nháp:**
   ```bash
   scripts/db/generate-ddl.sh
   ```
3. **Tạo file migration mới** với timestamp hiện tại:
   ```bash
   touch src/main/resources/db/migration/V$(date +%Y%m%d_%H%M)__<module>_<mô_tả>.sql
   ```
   Mở `build/schema/generated-ddl.sql`, **chỉ copy phần bạn vừa đổi** (file nháp chứa CẢ schema).
4. **Chỉnh lại** theo [mục 5](#5-quy-ước-sql) (thêm `default now()`, đặt tên FK/index, thêm FK
   sang bảng module khác...).
5. **Kiểm tra:**
   ```bash
   scripts/db/verify-migrations.sh
   ```
6. Commit chung với thay đổi entity: `feat(<module>): ...`.

### Ví dụ: thêm bảng mới

DDL nháp sinh ra kiểu này — chỉ cần bổ sung default, FK, index:

```sql
create table appointment_notes (
    id bigint generated by default as identity,
    appointment_id bigint not null,
    content text not null,
    created_at timestamptz not null default now(),   -- ← tự thêm default
    updated_at timestamptz not null default now(),   -- ← tự thêm default
    primary key (id)
);

alter table appointment_notes
  add constraint fk_appointment_notes_appointment_id
  foreign key (appointment_id) references appointments (id);

create index idx_appointment_notes_appointment_id on appointment_notes (appointment_id);
```

### Ví dụ: thêm cột

```sql
-- V20261101_0930__patient_add_nationality.sql
alter table patients add column nationality varchar(80);
```

Cột `not null` trên bảng **đã có dữ liệu** phải có default (hoặc thêm cột nullable → cập nhật dữ
liệu → `set not null`), nếu không migration lỗi trên DB của người khác:

```sql
alter table patients add column nationality varchar(80) not null default 'VN';
```

### Ví dụ: thêm giá trị enum

Enum lưu dạng `varchar` + ràng buộc `check (... in (...))`. Thêm giá trị vào Java enum mà **không**
sửa check → insert giá trị mới bị DB từ chối. Tên check do Postgres tự đặt:
`<bảng>_<cột>_check`.

```sql
-- V20261101_1000__appointment_add_rescheduled_status.sql
alter table appointments drop constraint appointments_status_check;
alter table appointments add constraint appointments_status_check
  check (status in ('HELD','CONFIRMED','CHECKED_IN','COMPLETED','CANCELLED','NO_SHOW','EXPIRED','RESCHEDULED'));
```

Không chắc tên check? Xem trong `psql`: `\d appointments`.

## 5. Quy ước SQL

| Thứ | Quy ước |
|---|---|
| Khoá chính | `id bigint generated by default as identity` (entity: `Long` + `GenerationType.IDENTITY`) |
| Thời gian | `timestamptz` (entity: `Instant`); ngày thuần: `date` (`LocalDate`) |
| `created_at` / `updated_at` | `not null default now()` |
| Enum | `varchar` + `check (... in (...))` — Hibernate tự sinh check khi dùng `EnumType.STRING` |
| Tiền | `numeric(15,2)` (entity: `BigDecimal`) |
| Foreign key | `fk_<bảng>_<cột>`, luôn `references <bảng> (id)`. Thêm cả FK sang bảng **module khác** |
| `on delete` | **Không** dùng `cascade` — dữ liệu y tế/thanh toán không được tự mất theo bản ghi cha |
| Index | `idx_<bảng>_<cột>`. Postgres **không** tự tạo index cho cột FK → thêm cho cột hay `where`/`join`; bỏ qua cột audit (`*_by_staff_id`, `created_by_user_id`) |
| Unique | `uq_<bảng>_<mô_tả>` |

**FK giữa module vs. rule "không quan hệ JPA xuyên module" trong README:** 2 chuyện khác nhau.
Rule README nói về **code Java** — entity lưu `Long patientId`, không `@ManyToOne` sang module
khác. Còn FK là ràng buộc ở **DB** để chặn ID không tồn tại; Hibernate không đọc FK nên không ảnh
hưởng gì tới entity.

## 6. Insert dữ liệu bằng SQL tay (seed, test thủ công, DBeaver...)

- **Tạo bản ghi cha trước** vì có FK: `users` → `patients`/`staffs`/`doctors` → ...;
  `clinics` → `rooms` → `doctor_schedules` → `doctor_schedule_slots` → `appointments`...
  Insert ID không tồn tại → lỗi `violates foreign key constraint "fk_..."`.
- `created_at`, `updated_at`, và các cột có default (`status`...) **không cần ghi**:
  ```sql
  insert into users (public_id, username, email, password_hashed, role)
  values (gen_random_uuid(), 'admin', 'admin@clinic.local', '<bcrypt-hash>', 'ADMIN');
  ```
- `updated_at` **không** tự cập nhật khi `update` bằng SQL tay (chỉ app — JPA auditing — làm
  việc đó). Cần thì tự ghi `updated_at = now()`.

## 7. Làm việc nhóm & merge

- Version dùng **timestamp** nên 2 người tạo migration song song không bị trùng version.
- Nhưng: nếu bạn đã chạy migration `V20261105_...` ở DB local, rồi pull về migration của
  teammate có timestamp **cũ hơn** (`V20261103_...`), Flyway từ chối khởi động (migration "lọt"
  vào giữa lịch sử). Cách xử lý:
  - **Branch chưa merge:** đổi tên file của bạn (hoặc của teammate, nếu chưa merge) sang timestamp
    mới hơn trước khi merge — được phép vì file chưa chạy ở môi trường chung nào.
  - **DB local:** reset DB (bảng ở mục 8).
- **Đã merge vào `main`** → file coi như đã chạy ở mọi nơi → **không đổi tên/sửa nữa**.

## 8. Xử lý sự cố

| Lỗi | Nguyên nhân & cách xử lý |
|---|---|
| `Validate failed: Migration checksum mismatch for migration version ...` | Ai đó **sửa file đã chạy**. Hoàn tác thay đổi trong file đó, đưa thay đổi sang migration mới. Nếu file chỉ mới chạy ở **DB local của bạn**: reset DB local |
| `Detected resolved migration not applied to database: ...` | Migration timestamp cũ hơn migration đã chạy (xem [mục 7](#7-làm-việc-nhóm--merge)). Reset DB local, hoặc đổi tên file nếu chưa merge |
| `Schema-validation: missing column [...] in table [...]` / `missing table` | Sửa entity mà **chưa viết migration**. Làm theo [mục 4](#4-quy-trình-thêm--sửa-bảng) |
| `Schema-validation: wrong column type encountered in column [...]` | Kiểu cột SQL khác kiểu field entity (vd. `integer` vs `Long`). Viết migration `alter column ... type ...` hoặc sửa entity |
| `violates foreign key constraint "fk_..."` khi insert tay | Bản ghi cha chưa tồn tại — xem [mục 6](#6-insert-dữ-liệu-bằng-sql-tay-seed-test-thủ-công-dbeaver) |
| `violates check constraint "..._check"` | Giá trị enum chưa có trong check — xem ví dụ "thêm giá trị enum" ở mục 4 |
| Reset DB local (xoá **toàn bộ dữ liệu** dev) | `docker compose down -v && docker compose up -d`, rồi `./gradlew bootRun` để chạy lại toàn bộ migration |
| Script `scripts/db/*.sh` báo cổng 55432 bị chiếm | `SCHEMA_DB_PORT=55433 scripts/db/verify-migrations.sh` |
